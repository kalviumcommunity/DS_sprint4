## Why Project Structure Matters

### The Problem with Disorganized Projects

**Scenario: A Disorganized Project**

```
my-project/
├── analysis.ipynb
├── script_v2.py
├── script_final.py
├── script_final_FINAL.py
├── data.csv
├── cleaned_data.csv
├── output.csv
├── results.csv
├── chart.png
├── chart_v2.png
├── README.txt
└── notes.txt
```

**What Goes Wrong?**

1. **Confusion**: Where is the raw data vs. cleaned data?
2. **Version Hell**: Which script is actually being used?
3. **Collaboration Breakdown**: A teammate can't find anything
4. **Reproducibility Issues**: Are outputs from which script?
5. **Scaling Problems**: Add 10 more projects = complete chaos
6. **Maintenance Burden**: 6 months later, even you forget what's what

**Real-World Impact:**

```
Time wasted looking for files:        2-3 hours per week
Accidental overwrites:                1-2 per month
Broken analysis from mixed data:      1-2 per quarter
Failed collaborations:                Prevents team projects
Hard to version control:              Git becomes messy
Can't reuse code:                     Start from scratch each time
```

### The Solution: Strategic Organization

**A Well-Organized Project:**

```
sales-prediction-project/
├── README.md
├── data/
│   ├── raw/                 # Original, never modified
│   └── processed/           # Cleaned, transformed data
├── notebooks/
│   ├── 01_exploratory_analysis.ipynb
│   └── 02_feature_engineering.ipynb
├── scripts/
│   ├── data_cleaning.py
│   └── model_training.py
├── outputs/
│   ├── models/
│   ├── visualizations/
│   └── reports/
├── configs/
│   └── parameters.yaml
└── .gitignore
```

**What Changes:**

1. **Clarity**: Anyone can navigate and understand
2. **Consistency**: Same structure across all projects
3. **Collaboration**: Easy to hand off to teammates
4. **Reproducibility**: Clear data flow and outputs
5. **Scalability**: Add new analysis without chaos
6. **Maintenance**: 6 months later, still obvious what's what
7. **Version Control**: Clean git history
8. **Reusability**: Can extract and reuse scripts

## The Core Principle: Separation of Concerns

### What is Separation of Concerns?

**Definition:** Keep different types of files in different places based on their role.

**The Roles:**

| Role | Purpose | Should Change | Location |
|------|---------|---------------|----------|
| **Raw Data** | Original source material | Never | `data/raw/` |
| **Processed Data** | Cleaned, transformed | Intermediate | `data/processed/` |
| **Code** | Scripts and notebooks | Frequently | `scripts/`, `notebooks/` |
| **Outputs** | Results, models, plots | Generated | `outputs/` |
| **Configuration** | Parameters, settings | When needed | `configs/` |
| **Documentation** | Guides, notes | Updated | `docs/`, root level |

### Why Separation Matters

**Without Separation:**
```
Project/
├── sales_data_FINAL.csv              ← Raw or processed?
├── sales_data_FINAL_2.csv            ← Which is current?
├── analysis.ipynb                    ← Which version?
├── analysis_v2.ipynb
├── results.csv
├── results_2.csv
├── plot1.png
```

**Questions That Can't Be Answered:**
- Is `sales_data_FINAL_2.csv` raw or cleaned?
- Which .ipynb was used to generate results?
- Which results.csv is current?
- Did plot1.png come from which version?

**With Separation:**
```
Project/
├── data/
│   ├── raw/
│   │   └── sales_data.csv            ← Original, never touched
│   └── processed/
│       └── sales_data_cleaned.csv    ← Generated by script
├── notebooks/
│   └── 01_analysis.ipynb             ← Only version needed
├── outputs/
│   ├── results/
│   │   └── summary_statistics.csv    ← Generated by notebook
│   └── visualizations/
│       └── trends.png                ← Generated by notebook
```

**What's Clear Now:**
- `data/raw/sales_data.csv` = original, never touch it
- `data/processed/sales_data_cleaned.csv` = generated by `01_analysis.ipynb`
- `outputs/results/summary_statistics.csv` = final results
- `outputs/visualizations/trends.png` = visualization

## Directory Hierarchy

### Minimum Structure (Simple Projects)

For small projects or experiments, this is sufficient:

```
project-name/
├── README.md
├── data/
│   ├── raw/
│   └── processed/
├── notebooks/
├── outputs/
└── .gitignore
```

**When to Use:** Quick analysis, learning projects, small datasets

**Example Projects:**
- "Analyze this CSV to answer a question"
- "Explore sales trends from 2 CSV files"
- "Train a simple classifier on iris data"

### Standard Structure (Most Projects)

For professional data science work, this is recommended:

```
project-name/
├── README.md
├── .gitignore
├── data/
│   ├── raw/
│   ├── processed/
│   └── external/
├── notebooks/
│   ├── 01_exploratory_analysis.ipynb
│   └── 02_model_training.ipynb
├── scripts/
│   ├── data_cleaning.py
│   ├── feature_engineering.py
│   └── model_training.py
├── outputs/
│   ├── models/
│   ├── visualizations/
│   └── reports/
├── configs/
│   └── parameters.yaml
└── requirements.txt
```

**When to Use:** Professional projects, team collaboration, production work

**Example Projects:**
- "Build a recommendation system for e-commerce"
- "Analyze customer churn with multiple data sources"
- "Create a demand forecasting model"

## Folder Purposes and Contents

### `data/` folder

**Purpose:** Store all data in project lifecycle

**Subfolders:**

#### `data/raw/`

**Purpose:** Original, immutable source data  
**Key Rule:** NEVER modify files here  
**What goes here:**
- Original CSV/Excel files
- Downloaded datasets
- API responses (saved)
- Database exports
- External data sources

**What does NOT go here:**
- Cleaned versions
- Transformed data
- Aggregated summaries
- Feature-engineered data

**Example:**
```
data/raw/
├── sales_data_2024.csv          # Downloaded from system
├── customer_demographics.xlsx   # External source
├── inventory_snapshot.csv       # Database export
└── competitor_pricing.csv       # API response
```

**Why immutable?**
- Preserves reproducibility (can always re-run cleaning)
- Safe backup (original always exists)
- Audit trail (know data source)
- Prevents accidental data loss

#### `data/processed/`

**Purpose:** Cleaned, transformed, analysis-ready data  
**What goes here:**
- Cleaned data (missing values handled, duplicates removed)
- Merged datasets
- Feature-engineered data
- Normalized/standardized data
- Aggregated datasets
- Train/test splits

**What does NOT go here:**
- Raw, unmodified files
- Temporary intermediate files (use temp folders)
- Large generated files (move to outputs)
- Personal experiments (use separate folders)

**Example:**
```
data/processed/
├── sales_data_2024_cleaned.csv
├── customer_demographics_merged.csv
├── features_engineered.csv
├── train_set.csv
└── test_set.csv
```

**Naming convention:**
- Include what was done: `sales_data_2024_cleaned.csv`
- Include date or version: `features_v2_final.csv`
- Be specific: `NOT data_processed_final.csv`

#### `data/external/`

**Purpose:** Reference data from external sources  
**What goes here:**
- Lookup tables (country codes, currency rates)
- Reference datasets
- Encoding tables
- Validation datasets
- Geographical boundaries
- Calendars, holidays

**Example:**
```
data/external/
├── country_codes.csv
├── exchange_rates.csv
├── us_holiday_calendar.csv
└── postal_code_regions.xlsx
```

### `notebooks/` folder

**Purpose:** Jupyter notebooks for exploration and analysis

**Naming Convention:** Use numbered prefix for sequence  
```
notebooks/
├── 01_exploratory_analysis.ipynb
├── 02_feature_engineering.ipynb
├── 03_model_training.ipynb
└── 04_model_evaluation.ipynb
```

**Why numbers?**
- Clear sequence of work
- Easy to sort chronologically
- Shows logical progression

**What goes here:**
- Exploratory data analysis
- Data quality checks
- Visualization experiments
- Model prototyping
- Results documentation

**What does NOT go here:**
- Production code (use `scripts/`)
- Reusable functions (extract to `scripts/`)
- Temporary test notebooks (keep locally)
- Multiple versions (`04_v1.ipynb`, `04_final.ipynb` = bad)

### `scripts/` folder

**Purpose:** Reusable, production-ready Python code

**What goes here:**
- Data cleaning functions
- Feature engineering functions
- Model training code
- Utility functions
- ETL processes

**What does NOT go here:**
- Notebooks (use `notebooks/`)
- One-off analysis (use notebooks first)
- Jupyter-specific code

**Example:**
```
scripts/
├── data_cleaning.py
├── feature_engineering.py
├── model_training.py
├── utils.py
└── config_loader.py
```

**Example Content (data_cleaning.py):**
```python
def load_and_validate(file_path):
    """Load CSV and check for required columns."""
    
def handle_missing_values(df, strategy='mean'):
    """Fill missing values using specified strategy."""

def remove_outliers(df, columns, method='iqr'):
    """Remove outliers using IQR or z-score method."""
```

### `outputs/` folder

**Purpose:** Generated files, results, models, visualizations

**Subfolders:**

#### `outputs/models/`

**Purpose:** Trained models and model artifacts  
**What goes here:**
- Serialized model files (.pkl, .joblib, .h5)
- Model metadata (accuracy, parameters)
- Feature importance files

**Example:**
```
outputs/models/
├── model_v1_baseline.pkl
├── model_v2_tuned.pkl
├── feature_importance.csv
└── model_performance.txt
```

#### `outputs/visualizations/`

**Purpose:** Generated plots and charts  
**What goes here:**
- Matplotlib/seaborn/plotly plots
- Dashboard screenshots
- Comparison charts
- Report figures

**Example:**
```
outputs/visualizations/
├── data_distribution.png
├── correlation_matrix.png
├── model_comparison.png
└── time_series_forecast.png
```

#### `outputs/reports/`

**Purpose:** Generated reports and summaries  
**What goes here:**
- Analysis summaries (HTML, PDF, markdown)
- Model reports
- Statistical summaries
- Export datasets for stakeholders

**Example:**
```
outputs/reports/
├── executive_summary.html
├── model_performance_report.pdf
└── customer_segment_analysis.csv
```

### `configs/` folder

**Purpose:** Configuration files and parameters

**What goes here:**
- YAML/JSON configuration files
- Parameter sets
- Database connection strings
- API endpoints
- Feature lists

**Example:**
```
configs/
├── data_config.yaml       # Data sources, paths
├── model_config.yaml      # Model hyperparameters
├── feature_config.yaml    # Features to engineer
└── paths_config.yaml      # File paths
```

**Example (data_config.yaml):**
```yaml
raw_data:
  source: ./data/raw/sales.csv
  encoding: utf-8
  
processed_data:
  output_path: ./data/processed/
  
validation:
  required_columns:
    - order_id
    - customer_id
    - amount
  date_format: '%Y-%m-%d'
```

### `docs/` folder (Optional but Recommended)

**Purpose:** Documentation about project and data

**What goes here:**
- Data dictionary: description of each column
- Model documentation: what the model does
- Setup instructions: how to run the project
- Architecture diagrams
- Reference materials

**Example:**
```
docs/
├── README.md                    # Project overview
├── data_dictionary.md           # Column descriptions
├── model_documentation.md       # Model details
├── setup_instructions.md        # Environment setup
└── architecture.md              # System design
```

## Naming Conventions

### File Naming Rules

#### Principle: Descriptive and Consistent

**❌ Bad Examples:**
- `analysis.ipynb` – Too vague
- `script_final_FINAL.py` – Multiple versions stored
- `data.csv` – What data?
- `output.pkl` – What output?
- `chart.png` – Which chart?

**✓ Good Examples:**
- `01_eda_customer_data.ipynb` – Clear purpose and data
- `data_cleaning.py` – Clear function
- `sales_data_2024_raw.csv` – Specific data, clearly raw
- `model_random_forest_tuned.pkl` – Model type and status
- `feature_importance_correlation.png` – Type and content

### Naming Strategy

**Format:** `[sequence]_[description]_[descriptor].[extension]`

**Examples by Type:**

**Notebooks:**
```
01_exploratory_analysis_customer_data.ipynb
02_feature_engineering_temporal.ipynb
03_model_training_baseline.ipynb
04_model_training_tuned.ipynb
05_model_evaluation_comparison.ipynb
```

**Scripts:**
```
data_cleaning.py              # Generic utility
feature_engineering.py        # Generic utility
model_training_random_forest.py
model_prediction.py
```

**Data Files:**
```
sales_data_raw_2024.csv
sales_data_cleaned_2024.csv
customer_demographics_merged_v2.csv
features_engineered_final.csv
train_set_80pct.csv
test_set_20pct.csv
```

**Models:**
```
model_baseline_initial.pkl
model_random_forest_tuned.pkl
model_neural_net_final_v3.h5
```

**Visualizations:**
```
feature_distribution_sales.png
correlation_heatmap_all_features.png
model_comparison_accuracy.png
time_series_forecast_30days.png
```

### Folder Naming Rules

**❌ Bad:**
```
analysis/
proj_data/
scripts_v2/
final_outputs/
NEW FOLDER/
```

**✓ Good:**
```
notebooks/
data/
scripts/
outputs/
configs/
```

**Rules:**
- Use **lowercase with underscores** (not spaces, not CamelCase)
- Use **singular for data folders** (`data/`, not `datas/`)
- Use **plural for collections** (`notebooks/`, `outputs/`)
- Be **specific** (`scripts/` not `code/`)
- Avoid **version numbers** in folder names (use git instead)

## Data Organization

### Raw Data Best Practices

**Rule 1: Keep Raw Data Immutable**

```python
# ❌ WRONG:
df = pd.read_csv('data/raw/sales.csv')
df.drop_duplicates(inplace=True)  # Modifying raw data!
df.to_csv('data/raw/sales.csv')   # Overwrote original!

# ✓ RIGHT:
df_raw = pd.read_csv('data/raw/sales.csv')
df_cleaned = df_raw.drop_duplicates()  # New variable
df_cleaned.to_csv('data/processed/sales_cleaned.csv')  # Save separately
```

**Rule 2: Document Data Sources**

Create a `data/raw/README.md`:

```markdown
# Raw Data Sources

## sales_data_2024.csv
- **Source:** Export from Salesforce CRM
- **Date Downloaded:** 2024-01-15
- **Records:** 50,000 rows
- **Columns:** order_id, customer_id, amount, date, region
- **Notes:** Includes cancelled orders (marked in status field)

## customer_demographics.xlsx
- **Source:** Customer Success database
- **Date Downloaded:** 2024-01-10
- **Records:** 25,000 rows
- **Notes:** Updates monthly; this is January snapshot

## competitor_pricing.csv
- **Source:** Web scraping (API endpoint)
- **Date Downloaded:** 2024-01-15
- **Records:** 5,000 products
- **Notes:** Pricing updated weekly
```

**Rule 3: Include Data Dictionary**

Create `docs/data_dictionary.md`:

```markdown
# Data Dictionary

## sales_data_2024.csv

| Column | Type | Description | Example |
|--------|------|-------------|---------|
| order_id | integer | Unique order identifier | 1001 |
| customer_id | integer | Customer identifier | 501 |
| amount | float | Order amount in USD | 1250.50 |
| date | date | Order date | 2024-01-15 |
| region | string | Geographic region | North America |
| status | string | Order status | Completed, Cancelled |
```

### Processed Data Best Practices

**Rule 1: Include Transformation Metadata**

Keep track of what was done:

```
data/processed/
├── sales_cleaned_v1.csv
├── sales_cleaned_v1_notes.txt     # ← Document transformations
├── sales_engineered_v2.csv
└── sales_engineered_v2_notes.txt
```

**Example notes file:**

```
Processing steps for sales_cleaned_v1.csv:

1. Source: data/raw/sales_data_2024.csv
2. Remove duplicates: 50,000 → 49,998 rows (2 duplicates)
3. Handle missing values:
   - 'amount': filled with median (n=15)
   - 'region': filled with 'Unknown' (n=3)
4. Remove outliers:
   - amount > $500,000 (n=2, likely data entry errors)
5. Date validation:
   - Removed 5 records with dates in future
6. Final result: 49,991 rows
7. Date created: 2024-01-16
```

**Rule 2: Version Control Processed Data Strategically**

```
data/processed/
├── sales_cleaned_v1.csv      # Keep early versions for comparison
├── sales_cleaned_v2.csv      # Show evolution if needed
└── sales_cleaned_LATEST.csv  # Point to current version in code
```

## Scripts and Code Organization

### Script Best Practices

**Rule 1: One Purpose Per Script**

```
✓ Good:
scripts/
├── data_cleaning.py          # Only cleaning functions
├── feature_engineering.py    # Only feature functions
├── model_training.py         # Only training code
└── utils.py                  # Helper functions

❌ Avoid:
scripts/
├── main_script.py            # Does everything (1000+ lines)
```

**Rule 2: Include Docstrings and Comments**

```python
# scripts/data_cleaning.py

def load_and_validate(file_path):
    """
    Load CSV file and validate required columns exist.
    
    Args:
        file_path (str): Path to CSV file
        
    Returns:
        pd.DataFrame: Loaded data
        
    Raises:
        FileNotFoundError: If file doesn't exist
        ValueError: If required columns missing
    """
    pass

def remove_duplicates(df):
    """Remove duplicate rows from dataframe."""
    pass
```

**Rule 3: Make Scripts Reusable and Testable**

```python
# ❌ NOT reusable:
if __name__ == '__main__':
    df = pd.read_csv('data/raw/sales.csv')
    df = df.drop_duplicates()
    df.to_csv('data/processed/sales.csv')

# ✓ Reusable:
def clean_sales_data(input_path, output_path):
    """Clean sales data and save to output path."""
    df = pd.read_csv(input_path)
    df = df.drop_duplicates()
    df.to_csv(output_path)
    return df

if __name__ == '__main__':
    clean_sales_data('data/raw/sales.csv', 'data/processed/sales.csv')
```

Every project needs a README:

```markdown
# Project Name

## Project Structure

- `data/raw/` - Original, immutable data

## Results

Key findings are in `outputs/reports/`.
```

## Common Mistakes to Avoid

### Mistake 1: Mixing Raw and Processed Data

```
❌ WRONG:
data/
├── sales_data.csv             # Is this raw or processed?
├── sales_data_v2.csv
├── sales_data_final.csv
└── sales_data_FINAL_REAL.csv

✓ RIGHT:
data/
├── raw/
│   └── sales_data_original.csv
└── processed/
    ├── sales_cleaned_v1.csv
    ├── sales_cleaned_v2.csv
    └── sales_engineered_final.csv
```

### Mistake 2: Multiple Notebook Versions

```
❌ WRONG:
notebooks/
├── analysis.ipynb
├── analysis_v2.ipynb
├── analysis_final.ipynb
├── analysis_FINAL_REAL.ipynb
└── analysis_FINAL_REAL_V2.ipynb

✓ RIGHT:
notebooks/
├── 01_exploratory_analysis.ipynb
└── 02_advanced_analysis.ipynb
# Keep evolving, use git for history
```

### Mistake 3: Disorganized Outputs

```
❌ WRONG:
outputs/
├── plot1.png
├── plot2.png
├── model.pkl
├── result.csv
├── result_new.csv
└── chart_FINAL.png

✓ RIGHT:
outputs/
├── models/
│   └── model_random_forest.pkl
├── visualizations/
│   ├── feature_distributions.png
│   └── model_comparison.png
└── reports/
    └── summary_statistics.csv
```

### Mistake 4: No Documentation

```
❌ WRONG:
# No README
# No data dictionary
# Unclear folder purpose
# Scripts with no comments

✓ RIGHT:
# README.md explaining purpose
# docs/data_dictionary.md with descriptions
# Logical folder hierarchy
# Scripts with docstrings and comments
```

### Mistake 5: Storing Everything in Notebooks

```
❌ WRONG:
# All code in notebooks
# Duplicate functions across notebooks
# Can't reuse code
# Hard to test

✓ RIGHT:
# Reusable functions in scripts/
# Import functions in notebooks
# DRY principle (Don't Repeat Yourself)
# Easy to test and maintain
```

### Shared Code Across Projects

**Problem:** Repeating utility functions across projects

**Solution 1: Shared Scripts Folder**
```
my-projects/
├── shared_code/
│   ├── data_cleaning.py
│   ├── viz_utilities.py
│   └── ml_utilities.py
├── project-1/
│   ├── data/
│   └── scripts/
│       └── project_specific.py
└── project-2/
    ├── data/
    └── scripts/
        └── project_specific.py
```

**Solution 2: Python Package**

```python
# shared_code_package/setup.py
from setuptools import setup
setup(
    name='shared_ds_tools',
    version='0.1.0',
    packages=['shared_ds_tools'],
)
```

Then import in projects:
```python
from shared_ds_tools.cleaning import remove_outliers
```

## Summary: Key Takeaways

### The Three Pillars of Good Project Structure

1. **Separation of Concerns**
   - Keep raw data separate from processed data
   - Keep exploratory code in notebooks, reusable code in scripts
   - Keep generated outputs separate from source data

2. **Consistency**
   - Use the same structure for every project
   - Use consistent naming conventions
   - Document consistently

3. **Clarity**
   - Anyone should understand your project in 2 minutes
   - Folder names should be self-explanatory
   - Include README and documentation

### A Well-Structured Project...

✓ Is easy for teammates to navigate  
✓ Preserves data integrity (immutable raw data)  
✓ Enables reproducible analysis  
✓ Facilitates code reuse across projects  
✓ Scales from single to complex projects  
✓ Follows industry best practices  
✓ Looks professional  

### Immediate Action Items

1. **Review** the standard structure for project types
2. **Adopt** a structure for your next project
3. **Document** your structure in a README
4. **Maintain** the structure as project grows
5. **Share** with teammates for consistency
