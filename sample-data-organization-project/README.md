# E-Commerce Sales Data Organization Project

## Project Overview

This project demonstrates best practices for organizing data throughout a data science workflow: raw data collection, processing, analysis, and output generation.

**Goal:** Analyze e-commerce sales trends and predict customer purchase behavior

**Status:** Learning example - shows proper data organization principles

## Key Principles Demonstrated

### 1. **Raw Data is Sacred**

Location: `data/raw/`

✓ Original files from sources (never modified)  
✓ Documented with source, date, and quality info  
✓ Read-only (protected from accidental changes)  
✓ Single version (source of truth)

### 2. **Processed Data is Traceable**

Location: `data/processed/`

✓ Generated from raw data transformations  
✓ Includes metadata files explaining changes  
✓ Clear naming showing transformation type  
✓ Versioned when multiple approaches compared  

### 3. **Outputs are Organized by Purpose**

Location: `outputs/`

✓ Models, visualizations, and reports separated  
✓ Generated by code (reproducible)  
✓ Can be regenerated from processed data  
✓ Timestamped for tracking  

### 4. **Everything is Documented**

✓ Data sources documented in `data/raw/DATA_SOURCES.md`  
✓ Processing steps recorded in metadata files  
✓ Data dictionary in `docs/DATA_DICTIONARY.md`  
✓ Reproducibility enabled through clear audit trails

## Workflow

```
1. COLLECT RAW DATA (no modification)
   ├─ data/raw/sales_transactions_raw.csv
   ├─ data/raw/customer_profiles_raw.csv
   └─ data/raw/product_catalog_raw.csv
   
2. DOCUMENT SOURCES
   └─ data/raw/DATA_SOURCES.md
   
3. PROCESS DATA (create new files)
   ├─ scripts/clean_sales_data.py
   ├─ scripts/engineer_features.py
   ├─ Output: data/processed/sales_cleaned.csv
   └─ Output: data/processed/customer_features.csv
   
4. DOCUMENT PROCESSING
   ├─ data/processed/sales_cleaned_metadata.txt
   └─ data/processed/customer_features_metadata.txt

   ├─ scripts/train_models.py
   ├─ Output: data/processed/train_set_80pct.csv

   ├─ scripts/train_models.py
   ├─ Output: outputs/models/customer_segmentation_kmeans.pkl
   └─ Output: outputs/models/purchase_prediction_xgboost.pkl

   ├─ scripts/train_models.py

8. CREATE REPORTS
   ├─ scripts/train_models.py
   └─ Output: outputs/reports/sales_analysis_2024.html
```

## How to Use This Example

### Understanding the Structure

1. Examine `data/raw/DATA_SOURCES.md` to understand data sources
2. Look at `data/raw/` folder - never modified files
3. Review `data/processed/` folder - created output files
4. Check `data/processed/*_metadata.txt` files for processing details
5. Explore `outputs/` organized by artifact type (models, viz, reports)

### Reproducing the Analysis

```bash
# 1. Navigate to project
cd sample-data-organization-project

# 2. Clean data
python scripts/clean_sales_data.py

# 3. Engineer features
python scripts/engineer_features.py

# 4. Train models and generate outputs
python scripts/train_models.py

# 5. Check outputs
ls outputs/
```

### Verifying Data Integrity

```bash
# Raw data should be unchanged
ls -la data/raw/
# (all files show original timestamps)

# Processed data should have metadata
head data/processed/*_metadata.txt

# Outputs should be recreatable
ls outputs/models/
ls outputs/visualizations/
```

## Best Practices Applied

✓ **Raw data isolated** - Never touch original files  
✓ **Clear separation** - Raw → Processed → Outputs  
✓ **Transparent naming** - File names indicate origin/purpose  
✓ **Complete documentation** - Sources, transformations, validation  
✓ **Reproducibility** - Can regenerate all artifacts from raw  
✓ **Audit trail** - Track who did what when and why  
✓ **Version control** - Track code changes, not large data files  
✓ **Metadata everywhere** - Know the story behind every file  

## Lessons to Apply to Your Projects

1. **Create the folder structure first** - Before any data processing
2. **Never modify raw data** - Even accidentally with `inplace=True`
3. **Create metadata files** - Document every transformation
4. **Use clear naming** - Anyone should understand file purpose
5. **Separate by stage** - Raw/Processed/Outputs are distinct
6. **Automate documentation** - Scripts generate processing records
7. **Test reproducibility** - Can someone else run your code?
8. **Organize outputs** - Models/visualizations/reports organized by type

## Quick Reference: The Three Rules

| Stage | Rule | Example |
|-------|------|---------|
| **Raw** | Never modify | `sales_transactions_raw.csv` (unchanged) |
| **Processed** | Create new file | `sales_cleaned.csv` (derived from raw) |
| **Outputs** | Regenerate daily | `sales_trend_2024.png` (from processed) |

## Questions?

**Why is this structure better?**
- Teammates understand data flow instantly
- Easy to find any file
- Reproducible: rerun scripts to get same results
- Trustworthy: can verify nothing was corrupted

**What if I have more data?**
- Add subfolders under processed/ (level_1_cleaned/, level_2_engineered/)
- Keep principles the same
- Document everything

**How do I scale this?**
- Same structure works for 1 GB or 1 TB of data
- Add more files to data/processed/ for different approaches
- Keep outputs organized by type and date
