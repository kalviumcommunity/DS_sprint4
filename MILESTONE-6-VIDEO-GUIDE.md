## SEGMENT 5: Scenario-Based Reasoning (MANDATORY)
**⏱ Duration: 5 seconds**  
**Cumulative Time: 2:00**

### The Scenario

Read this verbatim:

**"A teammate opens your notebook and says the code works, but they cannot understand what the notebook is doing or why certain steps exist. What documentation mistakes likely caused this, and how would better Markdown usage fix the problem?"**

### Expected Answer

Your answer should reference at least 2-3 of these Markdown elements:
- Headings for organization  
- Explanatory text before/after code
- Lists that break down process  
- Code formatting for clarity

### Example Good Answers

**Option A (Quick, references multiple elements):**

"The mistake was probably no headings and no explanation before code cells. If my notebook had clear headings for each section, a table of contents, and Markdown cells explaining why each step exists, my teammate would understand the flow immediately. Good Markdown acts like a guide: headings show structure, lists show steps, and explanations show intent. That's what was missing."

**Option B (References execution flow):**

"Without Markdown, code just appears with no context. My teammate didn't know: Why is this cell here? What does this code do? Where does it fit in the analysis? Better Markdown would explain the purpose before each code cell, use lists to break down complex procedures, and add headings so readers can navigate. That structure is essential for collaboration."

**Option C (Connects to readability):**

"The issue is probably my Markdown didn't explain key concepts. If I had used clearer headings, added explanatory text before each code section, included inline code formatting for variables, and used lists to show process steps, the notebook would be self-documenting. Right now, readers only see code. Good Markdown makes the analysis story clear."

### What NOT to Answer

❌ "I don't know"  
❌ Generic answers that don't reference Markdown  
❌ Answers that only mention code quality, not documentation  

### Exact Script to Record

**[At 1:55-2:00]**

Deliver your scenario answer (choose one of the example answers above or create your own based on the elements shown):

"The mistake was no Markdown explaining the code. Without clear headings, my teammate couldn't navigate the notebook structure. Without explanatory text before code cells, they couldn't understand the purpose. Lists would help break down complex steps, and inline code formatting would clarify variables. Better Markdown would have made this notebook self-explanatory."

## Common Recording Pitfalls to Avoid

❌ **Too fast pacing:** Rush through explanations so viewers can't follow  
✓ **Solution:** Speak naturally, pause between ideas

❌ **Unclear audio:** Microphone too far, background noise, mumbling  
✓ **Solution:** Test audio first, keep mic 6" from mouth, minimize background noise

❌ **Unfocused camera:** Shows desktop clutter, wrong application, distracting elements  
✓ **Solution:** Focus on notebook only, clear desktop, close other apps

❌ **Scenario answer too short:** Only 1-2 seconds, lacks detail  
✓ **Solution:** Aim for full 5 seconds, reference specific Markdown elements

❌ **Out of order:** Skip segments or show them in wrong order  
✓ **Solution:** Follow this guide step-by-step, don't improvise order
